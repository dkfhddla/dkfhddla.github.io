## 프로젝트 맥락과 역할

Shotloom에서 사용할 프랍·캐릭터·카메라 프리셋·맵을 등록·검증·제공하는 지원 프로젝트입니다. 에셋의 모델링·원화·애니메이션 제작과 공급 시스템 개발은 구분합니다.

초기 정적 라이브러리 구축부터 API 런타임·게시·전달 검증까지 대부분의 개발을 담당했습니다. 팀에서 정의한 계약과 동료의 후속 변경을 바탕으로 구현했습니다. 참여 기간 **2026.05.28–08.25**에는 인수인계 문서 작성이 포함되며, main 반영 개발 기록은 8월 18일까지입니다.

## 목록 조회와 파일 전달 분리

**문제:** 목록이 파일 위치와 직접 묶이면 제공 환경과 전달 정책이 달라질 때 편집기까지 영향을 받습니다.

**본인 기여와 구조:** 정적 V1의 원본·메타데이터, 빌드·서버와 HTTP 검증 경로를 구축했습니다. V2에서는 팀 계약을 바탕으로 단일 Node.js 리스너와 Catalog·Resolver·파일·readiness 경로를 구현했습니다.

1. **Catalog:** 사용할 수 있는 자산의 메타데이터와 참조값을 조회합니다.
2. **Resolver:** 참조값을 전달 정보로 해석합니다.
3. **파일 다운로드:** 편집기가 반환된 URL에서 에셋과 썸네일을 가져옵니다.

목록·전달 정책은 공급 시스템이, 가져온 자산의 장면 배치·편집은 Shotloom이 맡습니다. API 전환 뒤 구형 목록 경로와 fallback을 정리했습니다.

## 파일과 메타데이터를 같은 generation으로

**문제:** API 스냅샷과 실제 파일이 서로 다른 빌드 결과를 참조하면 목록에서는 정상인 자산도 가져오기에 실패할 수 있습니다.

**본인 기여:** 파일·카탈로그·스냅샷을 완성된 **generation**으로 묶고 검증했습니다. 검증한 후보를 불변 디렉터리로 게시하고 `current.json` 포인터를 원자적으로 교체했습니다. 서버는 실행 시 선택한 generation을 고정해 API와 파일이 같은 버전을 제공하도록 했습니다.

**결과와 절충:** 실행 중 버전 일관성을 우선했습니다. 새 generation 반영에는 서버 재시작이 필요하며 자동 reload·무중단 전환을 제공하는 구조로 주장하지 않습니다.

## 실제 다운로드와 배포 결과 검증

다운로드한 파일의 해시·크기·HTTP 메타데이터를 확인하고 Catalog → Resolver → 에셋·썸네일 바이트 경로를 검증했습니다. 배포된 Catalog에서 기대값까지 읽으면 같은 오류를 놓칠 수 있어, **배포 전 정식 빌드에서 만든 최소 기대 문맥**을 검증 입력으로 사용하도록 보강했습니다.

검증된 generation을 Docker 이미지에 포함하는 실행 방식과 이미지 검증 절차도 추가했습니다. 외부 DNS·TLS와 전체 인프라 구축은 본인 성과로 포함하지 않습니다.

## 확인된 결과와 범위

Shotloom에서 실제로 목록을 조회하고 프랍·캐릭터·맵을 씬에 추가하는 연동까지 사용했습니다. 독립 출시 제품이나 외부 고객 운영 완료로 표현하지 않습니다. 모든 개발 단계의 테스트·배포 검증이 통과했다고 일반화하지 않으며, 미병합 데이터 가져오기 파이프라인도 완료 기능에 포함하지 않습니다.

Codex 기반 구현·리뷰와 요구사항·계약 검토 방식은 [Shotloom 개발 경험](/projects/shotloom/#ai-개발에서-맡은-판단과-검증)에 연결합니다.
