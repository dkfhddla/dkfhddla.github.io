Shotloom의 첫 기능은 타임라인도, 3D 뷰포트도 아니었습니다. 가장 먼저 만들어진 것은 **책임의 경계**였습니다.

어떤 데이터가 프로젝트의 원본인지, 3D 장면의 실행 의미는 누가 결정하는지, 화면은 어디까지 책임지는지를 먼저 나눴습니다. 이 선택은 눈에 잘 보이지 않지만, 이후 수백 개의 변경이 하나의 제품으로 이어질 수 있었던 출발점이 됐습니다.

Shotloom은 하나의 촬영 단위인 **Shot**을 중심으로 캐릭터와 소품을 배치하고, 타임라인에서 동작과 카메라를 편집하는 도구입니다. 처음에는 브라우저에서 한 장면을 만들고 재생하는 편집기로 출발했습니다. 이후 작업물을 안전하게 저장하는 구조, 외부 생성 결과를 가져오는 파이프라인, 자동 렌더링과 서비스 경계, 손발 자세와 카메라를 정밀하게 다루는 도구까지 범위가 넓어졌습니다.

이 글에서는 그 변화를 여섯 단계로 나눠 살펴봅니다. 먼저 프로젝트 전체가 어떻게 발전했는지 정리하고, 마지막에 제가 직접 맡았던 부분만 별도로 구분해 기록합니다.

## 조사 기준

이 글은 2026년 8월 22일 Shotloom `main`을 기준으로 작성했습니다. 최초 커밋부터 당시 `main`까지의 커밋, 병합된 PR, 채택된 ADR, GitHub Release와 현재 저장소 구조를 함께 확인했습니다.

- 최초 커밋: 2026년 3월 13일
- 기준 시점 규모: 커밋 1,569개, 병합 PR 944개, ADR 109개, Release 10개
- 최신 Release: `v0.1.15`

GitHub 저장소가 만들어진 날짜는 4월 1일이지만, `main`에는 그보다 앞선 3월 13일의 초기 scaffold 이력이 남아 있습니다. 그래서 이 글은 저장소 생성일이 아니라 최초 커밋부터 시작합니다.

아래의 PR·ADR·Release 표기는 비공개 저장소에서 확인한 근거의 식별자입니다. 공개 블로그에는 링크와 내부 이슈·대화 내용을 싣지 않았습니다. 병합되지 않은 작업, 실제 운영 여부, 고객 사용 여부, 바이너리 에셋의 시각적 내용도 확인된 프로젝트 성과로 계산하지 않았습니다.

## 1. 제품과 아키텍처 경계를 먼저 세우다

초기 Shotloom은 무거운 3D 제작 도구 전체를 대체하려 하지 않았습니다. 하나의 장면 전체보다 **Shot과 camera clip을 가장 중요한 편집 단위**로 삼고, 브라우저에서 빠르게 장면을 구성하고 확인하는 데 범위를 맞췄습니다.

구현 책임도 처음부터 나뉘었습니다. Rust와 Bevy는 프로젝트 데이터의 규칙, 타임라인 평가, 3D 장면과 렌더링 같은 실행 의미를 맡았습니다. React와 TypeScript는 타임라인, 인스펙터, 아웃라이너처럼 사람이 조작하는 편집기 화면을 맡았습니다.

두 영역 사이에는 **typed bridge**를 뒀습니다. typed bridge는 화면이 3D 엔진의 내부 상태를 직접 건드리지 않고, 미리 정의된 명령과 이벤트로만 소통하게 하는 연결 계층입니다. 덕분에 화면과 엔진이 서로 다른 기술로 만들어져도 같은 데이터 계약을 기준으로 움직일 수 있었습니다.

이 시기의 결과는 화려한 기능이 아니라 이후 기능이 들어갈 자리를 만든 것이었습니다. Shot이 최상위 편집 단위라는 결정, Rust와 React의 소유권 분리, bridge를 통한 통신 원칙은 지금도 프로젝트의 기본 구조로 남아 있습니다.

**대표 근거:** 최초 scaffold, `ADR-0000`, `ADR-0002`, `ADR-0003`, `ADR-0007`

## 2. 설계를 실제로 편집 가능한 흐름으로 연결하다

4월부터는 문서에 있던 구조가 사용자가 조작할 수 있는 흐름으로 바뀌기 시작했습니다.

캐릭터를 놓을 기본 공간인 void stage가 생겼고, VRM 캐릭터를 불러올 수 있게 됐습니다. VRM은 사람형 3D 캐릭터를 표현하는 파일 형식입니다. 타임라인에는 재생과 정지, 트랙, 재생 위치가 연결됐고, 동작 clip을 만들고 옮기는 조작이 React에서 bridge를 지나 Rust 엔진까지 이어졌습니다.

3D 뷰포트에는 대상을 선택하고 화면 위 손잡이를 끌어 이동·회전시키는 **gizmo**가 들어왔습니다. 캐릭터 동작 구간인 performance clip과 카메라 구간인 camera clip은 같은 시간축에서 결정적으로 평가되기 시작했습니다. 같은 입력과 같은 시점이라면 같은 결과를 보여준다는 원칙이 실제 재생과 스크럽에 적용된 것입니다.

마지막으로 한 Shot에서 여러 카메라 후보를 다루는 **multicam**과 하나의 camera clip을 만드는 흐름이 들어오면서, 캐릭터를 불러오고 동작을 배치한 뒤 카메라로 장면을 확인하는 첫 번째 편집 루프가 완성됐습니다. `v0.1.2`는 이 골든 패스가 하나의 Release로 묶인 시점입니다.

**대표 근거:** `PR #9`, `PR #110`, `PR #116`, `PR #152`, `PR #182`, `PR #224`, `PR #255`, `PR #256`, `v0.1.2`

## 3. 화면 상태를 저장·복구 가능한 작업물로 바꾸다

편집 기능이 늘어나자 다음 문제는 명확했습니다. 화면에서 한 번 잘 움직이는 것만으로는 제작 도구가 될 수 없었습니다. 사용자가 만든 결과를 저장하고, 다시 열고, 문제가 있으면 이유를 설명할 수 있어야 했습니다.

Shotloom은 작업물을 **bundle**이라는 단위로 다루기 시작했습니다. bundle은 Shot의 데이터와 참조하는 에셋, 저장에 필요한 메타데이터를 함께 묶은 프로젝트 파일 구조입니다. 여러 명령을 한 번의 사용자 조작으로 묶는 transaction과 undo/redo가 들어왔고, 데스크톱 파일 시스템을 위한 HostFs와 브라우저 저장 공간인 OPFS가 연결됐습니다.

Asset Browser도 단순한 목록에서 실제 공급원과 연결되는 기능으로 발전했습니다. 로컬 Catalog에서 에셋 정보를 받고, 내려받은 bytes를 검증한 뒤 bundle 안에서 다시 찾을 수 있도록 provenance를 보존했습니다. provenance는 파일이 어디에서 왔고 어떤 과정을 거쳤는지를 추적하는 정보입니다.

이 단계에서 Shotloom의 작업 단위는 잠깐 존재하는 화면 상태에서 **검증하고 저장하고 다시 불러올 수 있는 bundle-owned state**로 바뀌었습니다. 이후 추가된 pose, camera key, 생성 에셋도 모두 이 소유권과 검증 규칙 위에 놓이게 됩니다.

**대표 근거:** `PR #338`, `PR #372`, `PR #373`, `PR #411`, `PR #418`, `ADR-0053`, `v0.1.5`~`v0.1.8`

## 4. 단일 편집기에서 생성 파이프라인의 중심으로 넓어지다

6월 중순부터 Shotloom은 사람이 처음부터 모든 것을 배치하는 편집기만을 목표로 하지 않게 됐습니다. 외부 시스템이 만든 초안을 검증된 작업물로 바꾸고, 사람이 그 결과를 다시 편집하는 흐름이 연결됐습니다.

**S2M**은 storyboard 형태의 입력을 Shotloom의 장면과 타임라인 구조로 바꾸는 과정입니다. S2M 입력에서 캐릭터와 카메라 정보를 읽고 bundle을 구성하는 기능이 단계적으로 들어왔습니다. **StoryPreviz**가 만든 카메라 템플릿도 Shotloom camera에 적용할 수 있게 됐습니다.

명령줄에서 bundle을 검증하고 이미지를 렌더링하는 **CLI**가 생기면서, 편집기 화면을 열지 않아도 같은 프로젝트 규칙으로 자동화할 수 있는 길이 열렸습니다. 브라우저와 데스크톱도 현재 편집 상태에서 이미지 결과를 만들 수 있게 됐습니다.

캐릭터 자세 생성은 **Text2Pose**로 정리됐습니다. Text2Pose는 문장으로 찾거나 생성한 자세를 캐릭터에 적용하는 흐름입니다. 검색용 개발 기능에서 시작해 pose 데이터, 외부 자세 생성 서비스인 provider 연결, 미리보기 저장, 브라우저 전송까지 확장됐습니다. 문장에서 시간에 따른 움직임을 만드는 초기 방식인 **T2M**은 주 제품 경로에서 물러나 호환과 검증을 위한 제한된 경계로 남았습니다.

이 변화로 Shotloom은 생성 결과의 종착지가 아니라, **생성 결과를 검증된 bundle로 바꾸고 사람이 다시 다듬는 중간 허브**가 됐습니다.

**대표 근거:** `PR #506`, `PR #551`, `PR #569`, `PR #709`, `PR #726`, `ADR-0085`, `ADR-0089`, `v0.1.11`~`v0.1.14`

## 5. 내부 기능을 제품 UI와 서비스 계약으로 정리하다

기능이 많아질수록 개발용 패널에 기능을 추가하는 방식은 한계가 생겼습니다. 7월 하순에는 내부 기능을 실제 사용 흐름에 맞춰 Shot Editor로 옮기는 작업이 진행됐습니다.

상단 도구 영역, 아웃라이너, 뷰포트, 속성 패널의 역할이 정리됐고 캐릭터·소품·카메라를 제품 화면에서 만들고 선택하고 수정할 수 있게 됐습니다. 개발자가 기능별 패널을 찾아다니는 구조에서, Shot 하나를 중심으로 작업하는 화면으로 이동한 것입니다.

에셋 전달 방식도 바뀌었습니다. **Asset Library v2**에서는 Catalog가 어떤 에셋이 있는지와 식별 정보를 제공하고, Resolver가 실제 파일을 받을 위치를 결정합니다. Shotloom은 임의로 주소를 만들지 않고, 두 계약을 통해 받은 bytes를 검증해 bundle에 넣는 소비자 역할을 맡았습니다.

동시에 **Shotloom Service**의 API와 실행 경계가 생겼습니다. Service는 HTTP 요청과 작업 순서를 조율하지만, bundle의 규칙과 렌더링 의미까지 새로 정의하지는 않습니다. 그 권한은 기존 Rust core와 runtime에 남았습니다. 실행 표면이 브라우저, 데스크톱, CLI, Service로 늘어났지만 중심 규칙을 여러 곳에 복제하지 않으려는 선택이었습니다.

`v0.1.15`는 Shot Editor, Asset Library v2, 생성·렌더 경로가 하나의 제품 흐름으로 묶인 전환점입니다.

**대표 근거:** `PR #802`, `PR #867`, `PR #873`, `PR #902`, `ADR-0095`, `ADR-0097`, `v0.1.15`

## 6. 생성 결과를 clip과 camera 단위로 정밀하게 다듬다

마지막 단계에서는 생성 결과를 가져오는 것보다 **가져온 결과를 어디에 저장하고 어떻게 안전하게 수정할지**가 중요해졌습니다.

수동으로 고친 pose의 소유권은 Shot 전체의 초기 상태가 아니라 각각의 `PerformanceClip`으로 이동했습니다. 같은 원본 자세인 **Source Pose**를 쓰는 인접 clip이라도 한 clip에서 고친 자세가 다른 clip으로 새지 않게 하기 위한 결정입니다. 현재의 평가 순서는 개념적으로 `Source Pose → clip-local manual override → runtime이 계산하는 IK → render`입니다.

여기서 **IK**는 손이나 발의 목표 위치를 지정하면 팔과 다리 관절이 그 위치에 맞도록 계산되는 기능입니다. 한 손에서 시작한 Clip Pose IK는 양손과 양발로 확장됐고, 뷰포트의 이동 gizmo에 이어 손바닥과 발의 방향을 바꾸는 회전 gizmo까지 연결됐습니다. React가 타임라인 평가 규칙을 복제하지 않고, 실제 pose를 계산하는 runtime이 활성 clip과 IK 동작의 권한을 갖도록 경계도 다시 정리했습니다.

카메라 쪽에서는 Shot마다 전체 길이를 덮는 camera clip 하나를 유지하고, 그 안의 개별 카메라인 **camera entry**와 시간별 카메라 값인 **camera key**를 실질적인 편집 단위로 삼는 규칙이 생겼습니다. 절대 위치 카메라와 캐릭터·소품을 기준으로 따라 움직이는 **target-bound camera**를 뷰포트에서 직접 조정할 수 있게 됐습니다.

캐릭터·소품·카메라의 배치 정보가 구조화된 **structured proxy scene**을 가져오는 경로도 Rust의 검증 경계와 공개 API 쪽으로 이동했습니다. 장면을 불러온 뒤 지면에 맞추고 카메라를 다시 평가하는 과정까지 보강되면서, 생성 장면을 사람이 이어서 편집할 수 있는 흐름이 더 단단해졌습니다.

**대표 근거:** `PR #987`, `PR #1012`, `PR #1022`, `PR #1035`, `PR #1038`, `PR #1043`, `PR #1044`, `PR #1053`, `PR #1054`, `ADR-0105`

## 프로젝트 전체와 내 기여를 나누어 보기

여기까지는 Shotloom 팀과 저장소 전체의 발전 과정입니다. 모든 변화가 제 기여였다는 뜻은 아닙니다.

아래에서는 GitHub 작성자가 `dkfhddla`이고 `main`에 병합된 것으로 다시 확인한 PR만 사용했습니다. 프로젝트의 모든 기능을 나열하기보다, 제가 반복해서 맡았던 연결부를 세 가지 흐름으로 정리했습니다.

### 1. Viewport와 camera를 실제 편집 경험으로 연결한 일

**문제:** 3D 엔진에 카메라와 장면이 있어도, 사용자가 브라우저에서 자연스럽게 이동하고 원하는 대상을 편집하지 못하면 제품 기능이 되기 어려웠습니다. 입력 처리가 화면과 runtime 여러 곳에 흩어지면 같은 조작도 모드에 따라 다르게 동작할 위험이 있었습니다.

**내가 맡은 부분:** 초기 웹 뷰포트의 camera navigation부터 timeline 조작과 engine bridge 연결을 구현했습니다. 이후 editor view와 cine-camera authoring의 경계를 나누고, 마우스와 키보드 입력을 `이동`, `회전`, `확대` 같은 의미 기반 navigation intent로 정리했습니다. 데스크톱 3D 도구에 익숙한 조작 방식도 같은 lifecycle 위에 연결했습니다.

**결과:** 뷰포트가 단순 미리보기 화면에서 장면과 카메라를 만들고 조정하는 저작 공간으로 발전했습니다. 입력 장치나 실행 환경이 달라져도 같은 의미의 조작을 runtime에 전달할 수 있는 기반이 생겼습니다.

**대표 근거:** `PR #84`, `PR #110`, `PR #116`, `PR #589`, `PR #700`, `PR #797`, `PR #806`

### 2. 작업물을 저장하고 렌더링과 에셋 전달까지 이어 준 일

**문제:** 편집한 장면이 화면에서만 존재하거나, 가져온 에셋의 원본 bytes와 출처가 저장되지 않으면 다시 열었을 때 같은 결과를 보장할 수 없습니다. 로컬 편집과 자동 렌더링이 서로 다른 프로젝트 규칙을 사용해도 결과가 갈라질 수 있습니다.

**내가 맡은 부분:** directory bundle 변환과 import한 에셋 bytes·thumbnail 보존을 구현하고, CLI 이미지 렌더 경로를 연결했습니다. Asset Library가 v2 Catalog·Resolver 계약으로 바뀔 때는 editor 소비 경로와 hosted source 전환을 맡아, 검증된 bytes가 bundle에 저장되는 과정으로 이어지도록 정리했습니다.

**결과:** 사용자가 가져온 에셋을 포함한 작업물을 저장하고 다시 불러올 수 있게 됐고, 같은 bundle 규칙을 편집기와 CLI 렌더가 공유하게 됐습니다. Asset Library의 전달 정책과 Shotloom의 소비·저장 책임도 분리됐습니다.

**대표 근거:** `PR #338`, `PR #411`, `PR #418`, `PR #506`, `PR #873`, `PR #902`

### 3. Clip Pose와 IK의 소유권을 제품 흐름으로 완성한 일

**문제:** 자세 수정이 Shot 전체 상태에 저장되면 인접한 performance clip 사이로 변경이 새어 나갈 수 있었습니다. UI가 활성 clip을 따로 계산하면 Rust runtime의 실제 평가 결과와 어긋날 가능성도 있었습니다.

**내가 맡은 부분:** manual pose override의 영속 소유자를 `PerformanceClip`으로 옮기고, 네 손발을 다루는 Clip Pose IK를 Shot Editor의 편집 흐름과 연결했습니다. 뷰포트의 이동·회전 gizmo로 IK target을 편집하게 만들고, 활성 clip과 동작 취소 판단은 실제 평가를 수행하는 runtime이 소유하도록 중복 로직을 제거했습니다.

**결과:** 자세 수정이 clip 단위로 저장·복구되고, 같은 Source Pose를 공유해도 서로 독립적으로 편집할 수 있게 됐습니다. 사용자는 Shot Editor에서 손발의 위치와 방향을 직접 조정할 수 있고, 재생 위치가 바뀔 때도 runtime의 평가 결과를 기준으로 안전하게 동작합니다.

**대표 근거:** `PR #987`, `PR #1010`, `PR #1011`, `PR #1022`, `PR #1034`, `PR #1035`

## 발전 과정에서 반복해서 배운 것

Shotloom의 변화는 기능이 많아진 역사이기도 하지만, 더 중요한 흐름은 **소유권을 계속 더 정확한 위치로 옮긴 과정**이라고 생각합니다.

- 화면과 runtime 사이에서는 명령과 이벤트의 계약이 상태의 주인을 분명하게 했습니다.
- 작업물에서는 bundle이 저장과 복구의 기준이 됐습니다.
- 에셋 전달에서는 Asset Library와 Shotloom의 책임이 Catalog·Resolver 경계로 나뉘었습니다.
- 자세 편집에서는 Shot 전체가 아니라 실제 변경이 살아 있는 performance clip이 데이터를 소유하게 됐습니다.

제 기여도 주로 이 연결부에 모여 있었습니다. 화면에 기능을 하나 더 추가하는 것보다, 사용자의 조작이 runtime의 규칙을 지나 저장 가능한 결과가 되고 다시 같은 모습으로 복구되는 흐름을 만드는 일을 반복해서 맡았습니다.

프로젝트 전체의 성과와 제 역할을 구분해 보니, 제가 어떤 문제를 계속 중요하게 봐 왔는지도 더 선명해졌습니다. 기능은 바뀌어도 책임의 경계를 정하고, 실행 결과와 저장 결과를 일치시키고, 확인 가능한 근거로 완료를 판단하는 방식은 앞으로도 계속 가져가고 싶은 기준입니다.
